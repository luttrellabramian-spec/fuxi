## 二、验收标准（已确认）

**功能全通**：v0.1.0 所有测试用例在 v0.2.0 中继续通过，不退化。

**性能基准**：

| 指标 | 目标 |
|------|------|
| 热记忆最大条目数 | 100 条（LRU 淘汰） |
| 热记忆大小上限 | 5000 char |
| LLM 单次调用超时 | 30 秒 |
| LLM 重试次数 | 3 次（指数退避） |
| gRPC 并发上限 | 100 请求 |
| 温记忆查询响应 | < 100ms（P99） |
| 系统内存上限 | 不超过 500MB（无泄漏）|

## 三、自进化设计约束（已确认）

- **建议自动生成**：系统自动从日志中分析失败模式，生成优化建议
- **执行需人工确认**：所有进化建议需人工审核后再写入生产系统
- **可解释性**：每次进化记录原因，方便回滚
- **不改变核心定位**：进化只优化能力，不改变伏羲的系统 prompt 核心定位

## 四、任务详细说明

### P0（两周内必须完成）

#### P0-1：热记忆 LRU 淘汰 + 大小上限

**问题**：v0.1.0 无淘汰机制，会话内存可能无限增长。

**方案**：
- 最大条目数：100 条，超出按 LRU 淘汰最旧条目
- 单条大小上限：5000 char，超出截断（保留最新部分）
- 热→温写入不受影响，新会话从空开始

**文件**：`python/src/memory/hot_memory.py`  
**负责人**：白  
**验收**：连续 10 轮对话内存不超 500MB，100 条以上触发淘汰

---

#### P0-2：LLM 超时控制 + 重试机制

**问题**：v0.1.0 LLM 调用无超时，可能无限等待。

**方案**：
- 单次调用超时：30 秒，超时抛异常
- 重试机制：3 次，指数退避（1s → 2s → 4s）
- 超时兜底：返回「当前思绪有点乱，稍等再试」+ 记录超时日志

**文件**：`python/src/llm/client.py`  
**负责人**：白  
**验收**：模拟 LLM 延迟 35 秒，触发超时 + 重试，第三次返回兜底回复

---

#### P0-3：执行日志结构化

**问题**：v0.1.0 无结构化日志，无法做进化分析。

**方案**：
- 每次 ReAct 循环记录一条 JSON 日志：
  - `timestamp`：时间戳
  - `session_id`：会话 ID
  - `cycle_count`：本轮循环次数
  - `success`：布尔值
  - `tools_used`：工具列表 + 调用结果
  - `llm_latency_ms`：LLM 响应时间
  - `error_type`：失败类型（timeout/tool_failure/llm_error/none）
- 存储位置：`logs/fuxi_execution_{date}.jsonl`
- 单文件最大：10MB，超出自动切分

**文件**：`python/src/engine/fuxi_engine.py`（新增日志模块）  
**负责人**：白  
**验收**：执行 5 轮对话，生成 5 条有效 JSONL 日志，可读可解析

---

### P1（两周内应该完成）

#### P1-1：温记忆 FTS5 索引 + 分页

**问题**：温记忆无索引，查询全表扫描。

**方案**：
- 对 `emotion_label`、`timestamp` 建 FTS5 复合索引
- 查询接口增加 `limit`、`offset` 参数
- 单次最多返回 50 条

**文件**：`python/src/memory/warm_memory.py`  
**验收**：1000 条数据，查询时间 < 100ms（P99）

---

#### P1-2：gRPC 连接池

**问题**：每次请求新建 channel，并发差。

**方案**：
- 复用 gRPC channel（单例模式）
- 心跳保活（每 30 秒一次 ping）
- 并发限制：max 100 请求，超出排队

**文件**：`python/src/grpc/server.py`  
**验收**：100 并发请求，无连接错误，日志无 channel 新建记录

---

#### P1-3：工具成功率追踪

**问题**：无法感知哪些工具经常失败。

**方案**：
- 每次工具调用记录：`tool_name / success / latency_ms`
- 每日汇总：成功率排名
- 失败率 > 30% 的工具降权（减少调度优先级）

**文件**：`python/src/engine/tool_manager.py`  
**验收**：工具调用日志可查，成功率排名可读

---

#### P1-4：TS 网关超时保护 + 降级

**问题**：TS 网关无降级，LLM 不可用时直接报错。

**方案**：
- 每个 API 请求独立 timeout（默认 25 秒，比 LLM 的 30 秒早触发）
- LLM 不可用时返回：`{ "status": "degraded", "message": "服务繁忙，请稍后重试" }`
- 不直接暴露下游错误堆栈

**文件**：`typescript/src/gateway.ts`  
**验收**：模拟 LLM 超时，网关返回降级 JSON，非 500 堆栈
